# Caja v1 (PWA offline-first + Spring Boot) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar Caja v1: una PWA que vende, cobra, cierra turno y respalda sin Internet, y sincroniza contra un backend central Spring Boot + PostgreSQL cuando la conexión vuelve.

**Architecture:** PWA React + TypeScript con IndexedDB como sistema de registro mientras no hay red. Toda escritura nace local y viaja por una cola de operaciones idempotente hacia un monolito modular Spring Boot. El backend es la fuente de verdad consolidada y el futuro Order Core; la caja es solo una fuente de pedidos más.

**Tech Stack:** Java 21, Spring Boot 3.3, Spring Web/Security/Data JPA, Hibernate, PostgreSQL 16, Liquibase, MapStruct, Bean Validation, JUnit 5, Testcontainers, Docker. React 18, TypeScript 5, Vite, React Router 6, Dexie 4, Zod, Tailwind, Workbox, Vitest, Testing Library, Playwright.

**Spec:** `docs/requisitos-v1.md` (contrato de v1) y `docs/superpowers/specs/2026-11-06-modelo-datos-design.md` (modelo físico aprobado). Contexto: `Panteamiento del proyecto.md`.

**Ejecución:** híbrida. Ver `docs/kickoff-implementacion.md`: modelo fuerte para tareas críticas y revisión; modelos livianos para tareas mecánicas.

## Global Constraints

- Moneda: pesos colombianos enteros. Backend `bigint`, frontend `number`. Prohibido `float` para dinero.
- Zona horaria `America/Bogota`. Backend almacena `timestamptz`; cada operación lleva `clientCreatedAt` y el servidor guarda además `serverReceivedAt`.
- Multi-tenant: toda tabla operativa lleva `tenant_id` y `location_id`. El servidor deriva el tenant del token, **nunca** del cuerpo del request.
- Toda escritura de venta nace en IndexedDB y se sincroniza. No existe un endpoint de “crear venta” directo: la creación pasa por `/api/sync/operations`.
- Idempotencia por `operationId` (UUID del cliente) y orden por `seq` monotónico por dispositivo. Un hueco en la secuencia devuelve `RETRY`, no se salta.
- Código visible: `LOCALIDAD-DISPOSITIVO-SECUENCIA` (ej. `ALM-A-000123`). La secuencia es local; el servidor la acepta y garantiza unicidad.
- El cierre de turno se calcula localmente y se sincroniza. El servidor recalcula y guarda ambas cifras; una diferencia entre ellas se marca.
- Operaciones administrativas (catálogo, usuarios, dispositivos, restauración) requieren conexión y rol `ADMIN`.
- Service Worker cachea solo el app shell. Nunca cachea respuestas de API.
- Respaldos: servidor `pg_dump` diario con retención 30/12; cliente exporta operaciones pendientes cada 5 minutos y antes de cerrar turno.
- TLS obligatorio en producción. El backend no se expone sin HTTPS.
- El repositorio git lo inicializa el usuario. Monorepo: `backend/`, `frontend/`, `infra/`, `docs/`.

## Decisiones que este plan asume

1. **IndexedDB con Dexie** como almacenamiento local (decisión tuya; sin spike previo).
2. **Autenticación offline:** token de dispositivo de larga duración para sincronizar + PIN local de 4–6 dígitos para desbloquear la caja. Cada operación lleva `userId` y el servidor valida que pertenezca al tenant y la sede. Las acciones administrativas exigen JWT online.
3. **Sin servidor local.** El backend vive en la nube; la caja solo necesita Internet para sincronizar y para operaciones administrativas.
4. **Pedido por venta:** cada venta crea un `Order` 1:1 en el servidor (`source = SALE`). El `Task Engine` y las estaciones quedan para fase 2.
5. **Devoluciones offline permitidas**, con motivo y usuario, igual que en el plan anterior.
6. **Día operativo = día calendario** en Bogotá, según el reloj del dispositivo; desfase > 5 min se marca al sincronizar.
7. **Un turno abierto por sede y dispositivo.** No hay sincronización entre cajas.
8. **Proveedor de nube pendiente**; el plan usa Docker Compose + Caddy para que el proveedor sea intercambiable.

## Riesgo aceptado

Se descartó el spike de persistencia. Para no repetir el problema del sistema anterior, las pruebas de persistencia y recuperación no son opcionales: son criterios de aceptación de las Tareas 9, 10, 11, 12, 13, 14 y 15. Si IndexedDB falla en la PC real, el diseño permite cambiar el repositorio local sin tocar los casos de uso.

## Review Focus

1. Dos reintentos de la misma operación crean dos ventas → `operationId` único y respuesta guardada.
2. Una venta llega antes que el turno que la contiene → `RETRY` por hueco de `seq`, sin venta huérfana.
3. El perfil del navegador se borra o se corrompe → las ventas pendientes se recuperan desde el export local.
4. El reloj de la PC está mal → el día operativo no cambia en silencio; se marca el desfase.
5. Un cliente forja `locationId` o `tenantId` en el payload → 403 y cero datos de otro tenant.

- [x] **Step 3: Implement the processor**
